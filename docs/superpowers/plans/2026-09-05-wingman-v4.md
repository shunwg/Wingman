# Wingman v4 — from a clickable demo to a product four strangers would trust

> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans`. Work streams are executed **in order**; each stream ends with `npm run verify` green, `npm run e2e` green, a screenshot pass, and a commit. Streams 0–2 are specified task-by-task below. Streams 3–10 are scoped here and each gets its own `docs/superpowers/plans/2026-09-05-ws<N>-<name>.md` written at the start of that stream, using the same bite-sized format.

**Goal:** Take the app from "a seeded demo that boots as a pre-verified user" to something a first-time stranger can install, register on, verify with BankID, add a flight to, and use safely; something an organiser can set up a verified circle in from a pasted list, with a mark, badges and chat; with every conversation in one inbox — and organised so a new engineer finds everything in one place. Done means Jobs and Thiel both score it ≥ 9.5/10.

**Architecture:** No new architecture. The four swappable axes and the five pure engines stay exactly as `CLAUDE.md` describes. Every new surface is a folder under `src/screens/` with a `use*.ts` hook; every new pure helper lives under `src/domain/` or `src/lib/` and compiles under the no-DOM `tsconfig.pure.json`; state changes go through `src/state/store.ts` with a versioned migration. The one real structural addition is `src/providers/flights/` (already aliased in five config files, never created).

**Tech stack:** Vite 6 · React 19 · TypeScript strict · Zustand + persist · Vitest 2 (pure + jsdom projects) · fast-check · Playwright (already a devDependency; no config yet). Design: Fraunces / Inter / JetBrains Mono, tokens in `src/design/tokens/`.

## Context

Wingman is at commit `a82a5b3` on `main`, deployed at https://shunwg.github.io/Wingman/. Nineteen commits took it from a single-file v2 prototype to a five-tab app with privacy, matching, stamps, meet rooms, multi-trip boards and circle invites. `npm run verify` is green (190 tests).

Three inventory passes (screens/flows, repo hygiene, stamps/design) and four persona walk-throughs found the same shape of problem everywhere: **the engines are finished and the doors to them were never built.** Concretely:

- There is no onboarding, sign-up, consent or welcome screen. The app boots as "Alex Ferrand", already BankID-verified, already in INSEAD, with three trips and an inbound request. `store.ts:106` has `onboarded: boolean` and `completeOnboarding()`; nothing reads or calls either.
- There is no way to add a trip. `BoardScreen`'s "Add a trip" button navigates to `#/trip`, which only lists seeded trips.
- `privacy/guardian/` (a full state machine, 19 tests), `privacy/audience/` (`whoCanSeeMe`, `previewAs`, 15 tests) are exposed by **no screen**. `blockPerson`, `removeTrip`, `markSeen` are store actions no UI calls. `expireIfDue` is tested and never runs, so a lapsed request waits forever.
- The meet room's fineprint says "you can still block them" — there is no block control on that screen, or on Person, or on Requests (only inside the decline sheet).
- The repo carries two generations side by side: eight v2 files loose in `src/` (125 KB, unreferenced), `build/` (3.3 MB), `wingman.html` (tracked *and* gitignored), `HANDOFF.md` describing npm scripts that no longer exist, `docs/STATUS.md` listing shipped phases as "next", `docs/design-plan.md` documenting a dark palette the app does not use. `docs/shots/` is 18 MB — 85 % of the tracked repo. `npm run e2e` has no config and no specs. CI deploys without running `verify`. `@tanstack/*` are declared and unused. No favicon, manifest, icon or logo exists.

The user asked for five voices on this — four users and one builder — a first-principles work list, folder organisation, BankID + registration + a first-use page, and a logo. They then answered four questions that this plan takes as decided:

| Decision | Answer |
|---|---|
| Type system | **Keep** Fraunces + Inter + JetBrains Mono. The `/taste` skill's Fraunces/Inter ban is overridden by the project's existing system (precedence: user → project system → skill). |
| Logo | **Two routes converging** — two thin arcs from opposite corners meeting at one ember dot. Never an airplane (banned motif in the original brief). |
| Order | Hygiene → Brand → **Onboarding → Safety → Trips → Events** → Discover/pro depth → Matching v2 → Polish → Wrap — **revised below** after the second brief |
| Privacy changes | All three: terminal shown only after the other person's first update; conservative defaults for new accounts; block + report on every person surface |

**Second brief (after the first plan draft):** circles must be set up from a list of email invites *or* email endings, carry a logo and badges, and have internal chat; every conversation the person is in — one-to-one meets, groups, circle channels — is tracked in one sophisticated, minimalist, user-friendly surface. Two more reviewers join: **Peter Thiel** (chairman and commercial adviser; *Zero to One*) and **Steve Jobs** (UI, UX, personality, commercial). The work is not finished until both score the app **≥ 9.5/10** on the scorecards in WS9. All feedback — users, builder, Thiel, Jobs, and every iteration — lives in `docs/reviews/2026-09-05-feedback.md`.

**Reorder, and why.** The second brief moves circles to the centre. Group chat cannot ship without block, report and mute (App Store Guideline 1.2 and finding W2 are both S1), so the safety surfaces are no longer a separate later stream — they are the first tasks of the Inbox stream. New order: **Hygiene → Brand → Onboarding → Circles (setup, admission, logos, badges) → Inbox (safety first, then meet / circle / group chat) → Trips → Events (organiser dashboard, QR, event board) → Discover & pro depth → Matching v2 → the Jobs/Thiel iteration loop + polish → Wrap.**

### 5 · The builder (ex-Tinder / Uber engineer-PM) — first principles

1. **Time-to-value under 60 seconds.** Install → one sentence about you → one flight → people. Anything that isn't one of those three is skippable, and BankID is *recommended*, not required, to see the board. Required to be seen by "ID-verified only" people — which is the incentive.
2. **Trust is visible in the flow, not on a settings page.** The privacy choice happens *before* the board, once, with a careful default. Block/report is on every surface that shows a person. What gets revealed at each step is said at that step.
3. **Liquidity is the product, and circles are the liquidity wedge.** An empty board kills retention; a live conference circle with 900 members guarantees density. Organiser mode is the sales tool.
4. **Double opt-in, always.** No free text before mutual yes (already true). Keep it.
5. **Scan, then read.** A board is scanned; a profile is read. Two card densities, one tap between them.
6. **Every screen ends in a next action.** No dead ends: the empty board says what to do; a settled trip says why; a closed request closes.
7. **Colour is never the only channel** (already a house rule). Terminal state, trip hue, stamp tone — all carry a label or glyph.
8. **Instrument, privately.** Local, aggregate, bucketed event counts (`seenCounts` is the start). No third-party analytics in a client-only app.
9. **One repo generation.** The v2 prototype leaves. Docs describe what is, not what was planned.
10. **Ship behind green.** `verify` + `e2e` in CI before deploy.

### 6 · Peter Thiel — chairman, commercial adviser

> "What valuable company is nobody building? Everyone builds an app for travellers. Nobody owns *the room* — the verified list of who is actually in this school, this conference, this flight. That is the secret. Own one room completely before you look at the airport."

Read through *Zero to One*'s seven questions:

| # | Question | Where Wingman stands | Finding | Stream |
|---|---|---|---|---|
| T1 | **Engineering** — 10× better, not 2×? | Proven admission (domain or list) + two-rule privacy is categorically different from LinkedIn's open noise and Tinder's unverified pool. The 10× is *trust per contact*, and today it is invisible: a viewer cannot tell a mocked stamp from a real one, and circles show a two-letter crest. | Make admission the hero of every circle surface: "Everyone here proved an @insead.edu address" is the product sentence, and the badge must be unforgeable in the UI. | WS3 |
| T2 | **Timing** — why now? | eID is ubiquitous in the Nordics (BankID 4.5 M users), the EU Digital Identity Wallet lands 2026, and every conference already ships an app nobody opens. | Say it in the memo and the pitch page; ship BankID-first onboarding (done in WS2). | WS2, WS9 |
| T3 | **Monopoly** — start small and dominate? | The plan is airport-first with circles as a feature. Wrong order. One school or one conference where *every* attendee is in the loop is a monopoly of a small market; the airport is the expansion, not the wedge. | Circles before trips in the order of work; an organiser can run a full event with members who have **no flight at all**. | WS3, WS4, WS6 |
| T4 | **People** — the right team? | Out of scope for the codebase; the memo lists the Mac/CI dependency and the moderation load. | — | — |
| T5 | **Distribution** — is there a channel? | Consumer install is the hardest channel there is. Selling to an organiser who pushes the invite to 1,200 badges is a channel with zero CAC. | Invite by email list, QR on the lanyard, short code on a slide; a pitch page for organisers; per-event pricing on the invite screen ("Free while in beta"). | WS3, WS6 |
| T6 | **Durability** — a moat in 10–20 years? | The verified-admission graph compounds: every circle joined makes the next admission cheaper (an INSEAD stamp is reusable). Local-only storage means nothing compounds yet. | Stamps and memberships are reusable across circles by design (already true in `privacy/`); note the Supabase seam as the point where the graph starts to exist. | WS3 |
| T7 | **Secret** — what do you know that others don't? | People will disclose more to a room they know is closed than to the open internet, and organisers will pay for the room, not the traveller. | Charge organisers; travellers are free. Never run ads. Say so on You. | WS9 |

Two more, in his words: *"Competition is for losers"* — do not position against LinkedIn or Tinder anywhere in copy; define the category ("verified rooms around the way you travel"). *"Sales matters just as much as product"* — the organiser demo (create a circle → paste 20 emails → QR → members chatting) must be flawless before anything else is polished. (T8)

### 7 · Steve Jobs — UI, UX, personality, commercial

> "Five tabs and a Requests inbox that is only requests. Where are my conversations? Make it one place. Make it obvious. Then make it beautiful."

| # | Finding | Stream |
|---|---|---|
| J1 | **One inbox.** Requests, meet rooms, circle chats and groups are four kinds of the same thing: a conversation. One list, sorted by what needs you, with a filter that is one row of chips. The Requests tab becomes **Inbox**. | WS4 |
| J2 | **Type a flight number and it fills itself in.** Forms are a failure of imagination. `SQ317` + a date should be the whole trip step for the common case. | WS5 |
| J3 | **The one sentence is the hero.** On the card it is (good). On the profile the portrait is 60 % of the screen; the app is professional-social, not a dating app — the sentence and the work line lead, the photo supports. | WS7 |
| J4 | **A circle has a face.** A two-letter crest is a placeholder. The organiser uploads the mark; the badge carries the mark; the inbox row carries the mark. | WS3 |
| J5 | **Say no.** Remove: the `Stand-in` chips from anything a viewer sees; the receipt's `dl` rows nobody reads; "Look again anyway" as a button on every settled trip. | WS4, WS7, WS9 |
| J6 | **One unforgettable moment.** Accepting a meet has a 1400 ms token reserved and nothing plays. Both cards slide in and lock, a stamp rotates in off-axis, the terminal line types itself. Once. Then never again on that screen. | WS9 |
| J7 | **It has to feel fast.** Press state on everything tappable within 130 ms (token exists, half the chips ignore it); route-level lazy loading so the first paint is the board, not 947 KB. | WS9 |
| J8 | **Personality.** The copy already has a voice ("a yes is not a commitment to keep talking"). Keep that voice everywhere and audit every string that does not sound like it. No "Submit", no "Error", no "Success". | WS9 |
| J9 | **Dark mode is not a filter.** Only the gallery has been seen dark. Every screen, both themes, before anyone calls it done. | WS9 |
| J10 | **Commercial:** the product people pay for is the organiser flow. It gets the same care as the consumer flow, and the organiser's first ten minutes decide the sale. | WS3, WS6 |

The ui-ux-pro-max checklist items adopted: 44 × 44 px touch targets with ≥ 8 px gaps · visible focus rings · 4.5:1 text contrast · skippable onboarding with Back · URL reflects state (hash routing already) · `React.lazy` for routes · no emoji as icons · `prefers-reduced-motion`. Its palette/typeface suggestion (rose + Lexend) is generic and is **not** adopted.

The `/taste` rules adopted: max one accent (ember — already), one radius system (already: pill for interactive, 16/24 for cards), full state cycles (empty/error/loading), label-above-input, no placeholder-as-label, real images not fake screenshots (the welcome page uses the unreferenced `src/assets/hero-terminal.jpg`), copy self-audit before ship, no em-dash flourishes in UI copy.

```ts
/**
 * The inverse of `localTime`: a wall-clock `HH:MM` on a local calendar date,
 * in a zone, as a UTC instant. This is the single place local time enters the
 * domain from the outside; forms hold strings, the domain holds instants.
 *
 * Method: assume the wall clock is UTC, read what that instant looks like in
 * `zone`, and shift by the difference. One correction pass covers DST edges;
 * a time inside a spring-forward gap resolves to just after the jump.
 */
export function utcFromLocal(date: ISODate, hhmm: string, zone: IanaZone): ISODateTime {
  const [h, m] = hhmm.split(':').map(Number) as [number, number];
  const [y, mo, d] = date.split('-').map(Number) as [number, number, number];
  let guess = Date.UTC(y, mo - 1, d, h, m);
  for (let i = 0; i < 2; i++) {
    const seen = wallClockMs(guess, zone);
    const want = Date.UTC(y, mo - 1, d, h, m);
    if (seen === want) break;
    guess += want - seen;
  }
  return new Date(guess).toISOString().replace(/\.\d{3}Z$/, 'Z') as ISODateTime;
}

function wallClockMs(ms: number, zone: IanaZone): number {
  const p = Object.fromEntries(
    new Intl.DateTimeFormat('en-GB', {
      timeZone: zone, hourCycle: 'h23',
      year: 'numeric', month: '2-digit', day: '2-digit', hour: '2-digit', minute: '2-digit',
    }).formatToParts(new Date(ms)).map((x) => [x.type, x.value]),
  );
  return Date.UTC(+p.year!, +p.month! - 1, +p.day!, +p.hour!, +p.minute!);
}
```

export function validateTripEntry(e: TripEntry, airports: AirportIndex, now: ISODateTime): TripEntryError[] {
  const errs: TripEntryError[] = [];
  const at = (field: string, message: string) => errs.push({ field, message });
  if (e.segments.length === 0) at('segments', 'Add at least one flight.');
  let prevArrive: ISODateTime | undefined;
  e.segments.forEach((s, i) => {
    const p = i === 0 ? '' : `segments.${i}.`;
    const from = airports.get(s.from), to = airports.get(s.to);
    if (!from) at(`${p}from`, 'Pick an airport from the list.');
    if (!to) at(`${p}to`, 'Pick an airport from the list.');
    if (from && to && s.from === s.to) at(`${p}to`, 'Arrival has to be somewhere else.');
    if (!HHMM.test(s.departLocal)) at(`${p}departLocal`, 'Use 24-hour HH:MM.');
    if (!HHMM.test(s.arriveLocal)) at(`${p}arriveLocal`, 'Use 24-hour HH:MM.');
    if (s.flightNo && !FLIGHT.test(s.flightNo.trim())) at(`${p}flightNo`, 'Looks like SK1465 or BA 767.');
    if (from && to && HHMM.test(s.departLocal) && HHMM.test(s.arriveLocal)) {
      const { departUtc, arriveUtc } = instants(s, airports);
      if (departUtc <= now) at(`${p}date`, `That is before ${now.slice(0, 10)}. Wingman only lists journeys ahead of you.`);
      if (prevArrive && departUtc <= prevArrive) at(`${p}departLocal`, 'This leg leaves before the previous one lands.');
      if (i > 0 && e.segments[i - 1]!.to !== s.from) at(`${p}from`, 'A connection starts where the previous leg landed.');
      prevArrive = arriveUtc;
    }
  });
  if (e.stay && prevArrive) {
    const last = e.segments[e.segments.length - 1]!;
    const landed = localDate(prevArrive, airports.zone(last.to));
    if (e.stay.until < landed) at('stay.until', 'You cannot leave before you land.');
  }
  return errs;
}

function instants(s: SegmentEntry, airports: AirportIndex) {
  const departUtc = utcFromLocal(s.date, s.departLocal, airports.zone(s.from));
  let arriveUtc = utcFromLocal(s.date, s.arriveLocal, airports.zone(s.to));
  if (arriveUtc <= departUtc) arriveUtc = utcFromLocal(nextDay(s.date), s.arriveLocal, airports.zone(s.to));
  return { departUtc, arriveUtc };
}

function nextDay(d: ISODate): ISODate {
  const t = new Date(`${d}T00:00:00Z`); t.setUTCDate(t.getUTCDate() + 1);
  return asISODate(t.toISOString().slice(0, 10));
}

export function buildTripFromEntry(
  e: TripEntry, airports: AirportIndex, ids: { tripId: TripId; personId: PersonId; now: ISODateTime },
): Trip {
  const segments: FlightSegment[] = e.segments.map((s, i) => {
    const { departUtc, arriveUtc } = instants(s, airports);
    const flightNo = (s.flightNo ?? `${s.from}–${s.to}`).replace(/\s+/g, '').toUpperCase();
    return {
      id: asSegmentId(`${ids.tripId}.${i}`),
      flightNo,
      carrier: s.flightNo ? flightNo.match(/^[A-Z0-9]{2,3}/)?.[0] ?? '' : '',
      from: s.from, to: s.to, departUtc, arriveUtc,
      ...(s.terminalFrom ? { terminalFrom: s.terminalFrom } : {}),
      ...(s.terminalTo ? { terminalTo: s.terminalTo } : {}),
      source: 'manual', confidence: 0.75,
    } as FlightSegment;
  });
  const last = segments[segments.length - 1]!;
  const lastEntry = e.segments[e.segments.length - 1]!;
  const toZone = airports.zone(lastEntry.to);
  const stays = e.stay ? [(() => {
    const city = airports.city(lastEntry.to);
    return {
      cityKey: city.key,
      dates: { from: localDate(last.arriveUtc, toZone), to: e.stay!.until },
      arriveUtc: last.arriveUtc,
      departUtc: utcFromLocal(e.stay!.until, '12:00', toZone),
      destination: { lat: city.lat, lon: city.lon, label: e.stay!.areaLabel ?? city.name },
    };
  })()] : [];
  return {
    id: ids.tripId, personId: ids.personId,
    ...(e.label ? { label: e.label } : {}),
    segments, layovers: [], stays,
    visibility: { listing: 'listed' },
    createdAt: ids.now,
  } as Trip;
}
